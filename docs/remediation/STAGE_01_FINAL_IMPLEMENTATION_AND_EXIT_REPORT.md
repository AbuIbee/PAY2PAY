**Exact function changed:** `findProductionFactoryCoordinatorCall` (the SV-007 AST identification helper). `assertSeventhArgumentIsPaymentInitiationVerified` and `assertFactoryWiresPaymentInitiationVerified` were **not** modified — they already satisfied every structural requirement.

**Before/after identification mechanism:**
- *Before (004-B state):* select the top-level `FunctionDeclaration` literally named `getFailedPaymentRetryCoordinator` (accepting the LAST one found if more than one existed, and regardless of whether it was exported); read its `return <identifier>;`; scan its body (skipping nested function/arrow/method bodies) for an assignment `<identifier> = new DrizzleFailedPaymentRetryCoordinator(...)`, matching purely by identifier TEXT.
- *After (this order):* (1) collect only top-level `FunctionDeclaration`s with that exact name that also carry an `export` modifier — zero throws "no exported factory," more than one throws "ambiguous"; (2) read the single exported factory's `return <identifier>;`; (3) reject up front if the factory's OWN parameter list declares that identifier (a self-shadowing parameter); (4) scan the same reachable region as before (never descending into nested functions), but now ALSO watching for any `let`/`const`/`var` declaration, catch-clause binding, or destructuring pattern that declares the same identifier anywhere in that reachable region — if found, fail closed with an explicit shadow error, before ever reaching the 0-candidate/ambiguous-candidate checks.

**Export validation:** `isExportedFunctionDeclaration` checks `ts.canHaveModifiers`/`ts.getModifiers` for `ts.SyntaxKind.ExportKeyword`. An unexported same-named function, a nested function, a function expression, or a same-named identifier that isn't a `FunctionDeclaration` at all are all structurally invisible to the collection step — never selected, never merely "not preferred."

**Cache-binding identity:** established by the exported factory's own `return <identifier>;` statement — the exact identifier text returned is the only name the assignment-search will ever match against; it is not hardcoded to the literal string `cached`.

**Shadow protection:** a single boolean (`shadowed`), set by the SAME traversal that harvests candidate assignments (so its scoping is guaranteed identical — it never enters a nested function/arrow/method body, exactly mirroring the harvester's own boundary), plus one explicit up-front check of the factory's own parameter list. Any declaration match sets `shadowed = true`; after traversal, `shadowed` is checked and thrown BEFORE the 0/1/many-candidate logic runs, so a shadowed source never reaches "accept" via a coincidentally-correct-looking assignment.

**Parenthesized-expression behavior:** unchanged from 004-B — `unwrapParens` loops while the node is a `ParenthesizedExpression`, so it already handled arbitrary nesting; SV7-19 (new) explicitly exercises two nested layers to confirm this, since 004-B's own R4 test only exercised one layer.

**Ambiguity behavior:** three independent ambiguity paths now exist, each fails closed: (1) more than one top-level exported factory declaration with the right name; (2) the factory's own parameter shadowing the returned name; (3) more than one qualifying assignment (or any qualifying assignment coexisting with a shadow) within the factory's own reachable body.

**False-pass prevention:** the original Codex false-pass (R3/SV7-07 — parenthesized, misconfigured production call plus an unrelated correctly-configured function) is preserved exactly as 004-B left it — confirmed still rejected (Section D). The NEW false-pass (004-BV-001's exact shadowing reproduction, SV7-02) is now independently rejected, using the literal source Codex supplied in this order's Section 7.
