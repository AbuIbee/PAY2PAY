# PAY2PAY Rollback Plan

**Added:** SPRINT_20_ClosedBetaReadiness, one of the four documents this sprint's spec requires by
name. This is a short, action-oriented rollback playbook for closed beta — the underlying mechanics
and evidence it relies on already live in `docs/OPERATIONS_BACKUP_RECOVERY.md` and
`docs/LAUNCH_RUNBOOK.md`; this document does not repeat that evidence, it tells you which button to
push and in what order.

## 1. Decide what kind of rollback you need

| Symptom | Rollback type | Go to |
|---|---|---|
| A new deploy broke something (bad code, not bad data) | Application rollback | §2 |
| A migration applied incorrectly, or a bad write corrupted data | Data-level fix | §3 |
| One specific feature (payments, bank connections, signups) is actively causing harm right now | Kill switch (no deploy) | §4 |
| The database itself is unreachable or corrupted | Database incident | §5 |

## 2. Application rollback (bad code, database unaffected)

**This is fully proven and safe today.** Every production deploy is an immutable, independently
addressable Vercel build (`docs/OPERATIONS_BACKUP_RECOVERY.md` §2).

1. `vercel ls pay-2-pay --prod` (or the Vercel dashboard) to find the last known-good deployment.
2. `vercel rollback <deployment-url>` (or "Promote to Production" in the dashboard) — this points
   production traffic at the previous build immediately, with no code change and no database change.
3. Confirm via `curl -sI https://paid2you.com` (200) and `GET /api/admin/health` (all dependencies
   healthy).
4. Root-cause the bad deploy on a branch; do not re-deploy `master` until the fix is verified in CI
   and, ideally, a PR preview.

**No "down" migration exists for any migration in this project** — every migration to date is
additive (new tables/columns, never a destructive `DROP`/type-narrowing). Rolling back the
application code while a newer, additive migration is still applied is safe by construction: older
application code simply does not reference the new column/table.

## 3. Data-level fix (bad migration or bad write, not a full outage)

**Forward-fix, not down-migration** — this project's established pattern
(`docs/OPERATIONS_BACKUP_RECOVERY.md` §2). Write a new, small, additive migration that corrects the
problem, following the same dual-file convention every prior migration uses
(`drizzle/migrations/NNNN_*.sql` generated by `drizzle-kit`, then a hand-authored
`supabase/migrations/<timestamp>_*.sql` copy with the `REVOKE ALL ... FROM anon, authenticated;`
statement appended). Never hand-edit a row directly against production without going through this
same reviewed, applied-via-migration path — an unreviewed manual UPDATE against production leaves no
audit trail and cannot be replayed if the fix itself turns out to be wrong.

If a migration is genuinely destructive (a real `DROP COLUMN`, a type narrowing that loses data), it
must be preceded by a Product-Owner-reviewed written plan — no migration in this project's history
has needed this, and none should be written casually.

## 4. Kill switches (fastest option — no deploy, no rollback)

Flip an environment variable in Vercel; each takes effect on next request, no redeploy required
(`docs/OPERATIONS_BACKUP_RECOVERY.md` §5, `src/lib/feature-flags.ts`):

| Flag | Effect when set to `false` |
|---|---|
| `FEATURE_PAYMENT_INITIATION_ENABLED` | Blocks new payment creation (503). Existing idempotent replays of already-created payments still succeed. Historical records untouched. |
| `FEATURE_BANK_CONNECTION_ENABLED` | Blocks new bank-account connections (503). Already-connected accounts and their ACH mandates are unaffected. |
| `FEATURE_CLOSED_BETA_ENABLED` | Set to `true` mid-incident to require an admin-issued invite code for every new signup — stops a signup-abuse incident without a deploy. |
| `EMAIL_DELIVERY_ENABLED` / `SMS_DELIVERY_ENABLED` | Set to `false` to stop outbound communications immediately (falls back to console-log-only, matching pre-production behavior). |

These are the correct first response for a live, in-progress incident (§ below and
`docs/OPERATIONS_BACKUP_RECOVERY.md` §3's severity table) — they buy time to root-cause without an
application rollback or a data-level fix.

## 5. Database incident (unreachable, corrupted, or needs restoring)

**Current, disclosed limitation, unchanged by Sprint 20**: the linked production Supabase project has
zero backups and PITR disabled (`docs/OPERATIONS_BACKUP_RECOVERY.md` §1) — **DEFERRED by explicit
Product Owner decision**, not required during the current pre-production/closed-beta window, but
**must be enabled and verified before real financial transactions occur.** Today, there is no way to
restore this database from data loss or corruption beyond a manual, not-currently-scheduled
`pg_dump`. If a database incident occurs during closed beta:

1. Diagnose via `GET /api/admin/health` — confirms whether Supabase itself is unreachable (a Supabase
   platform incident, wait for their recovery) versus a schema/data problem in a database that is
   still reachable (go to §3, forward-fix).
2. If real data loss occurred and no backup exists, this is a **SEV-1 incident**
   (`docs/OPERATIONS_BACKUP_RECOVERY.md` §3) — notify the Product Owner immediately; there is no
   silent recovery path.
3. Because the ledger is append-only and every payment/webhook event is deduplicated on a stable key
   (`docs/OPERATIONS_BACKUP_RECOVERY.md` §4), a *future* restore (once PITR is enabled) cannot
   double-apply a financial effect — but this has not been exercised against a real restore yet, and
   should be drilled (via a Supabase branch, never a destructive production restore) once PITR is on.

## 6. Who can execute a rollback

Vercel/Supabase account access ownership is a Product-Owner-held fact this document cannot state
(`docs/LAUNCH_RUNBOOK.md` §1). Before closed beta admits any user outside the existing team, confirm
at least one person other than the Product Owner has been granted the access needed to execute §2 and
§4 above during an incident — this is a genuine open item, not yet verified as resolved.
