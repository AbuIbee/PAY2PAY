# Production Launch Runbook

"PAID2YOU — MASTER P0" (2026-10-03), Section 62. Used by the OWNER during Days 4-5. No secret
values appear in this document — only actions, variable names, and expected outcomes. Each step
names whether a failure there means **STOP LAUNCH**.

| # | Action | Expected result | Failure result | Stop launch? |
|---|---|---|---|---|
| 1 | Point production DNS at the deployment; set `APP_URL` to the real domain | `APP_URL` resolves to the canonical production origin | `getServerEnv()`'s own `superRefine` throws `EnvironmentValidationError` if `APP_ENV=production` and `APP_URL` still resolves to localhost | YES |
| 2 | Confirm the production Postgres database is reachable | Application boots; `DATABASE_URL` connects | Boot fails immediately — nothing else in this list can proceed | YES |
| 3 | Take a backup of the production database (even if newly created) before applying migrations | A restorable snapshot exists | No rollback path if a migration behaves unexpectedly | YES |
| 4 | Run `npm run db:upgrade-production` (requires `DATABASE_URL` and a linked Supabase project — `supabase link` / `SUPABASE_PROJECT_REF`, same as `scripts/check-schema-drift.mjs`) — **do NOT run `supabase db push --linked` or apply `supabase/migrations/*.sql` manually/directly; use this command instead.** Codex found that applying every pending migration first (including `20261003040000_final_rbac_role_id_constraints.sql`) and only afterward running the legacy-role backfill is a real deployment-ordering defect — `scripts/run-production-upgrade.mjs` is the one script that GUARANTEES the backfill runs before that constraint migration ever reaches the database, by deferring that migration (and everything after it) until the backfill is confirmed complete. See `docs/CODEX_P0_VERIFICATION_HANDOFF.md`'s "P0-1" section for the exact mechanism and its own passing rehearsal (`npm run db:upgrade-orchestrator-rehearsal`). | All migrations apply cleanly, in the required safe order; the backfill runs automatically wherever it's needed (a guaranteed no-op on a database with no pre-existing legacy-role data) and is verified complete before the role_id-required constraint is ever applied | The script fails loudly and stops BEFORE applying the constraint migration if the backfill did not resolve every qualifying row, or if `supabase db push --linked` itself fails — stop and diagnose; do not work around it by applying migrations manually | YES |
| 6 | Confirm Supabase Storage project/bucket (`agreement-pdfs`, private) exists; set `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` | `npm run production-readiness` reports `SUPABASE_STORAGE: CONFIGURED` | Signed-agreement PDF storage fails closed (`ConfigurationError`) — Agreements can still be created, but PDF generation/retrieval will error | NO (but fix before Day 5's agreement-signing test) |
| 7 | Confirm Resend production key + verified sending domain; set `RESEND_API_KEY`/`EMAIL_FROM_ADDRESS` | `npm run production-readiness` reports `RESEND: CONFIGURED`; a real test email arrives | Production email fails closed (throws, never silently "sent") — invitations/notifications will visibly fail rather than silently vanish | YES (staff/agreement invitations depend on this) |
| 8 | Confirm Middesk production account; set `MIDDESK_API_KEY`, `MIDDESK_WEBHOOK_SECRET`, `BUSINESS_VERIFICATION_PROVIDER=middesk` | `npm run production-readiness` reports `MIDDESK: CONFIGURED` | Business verification fails closed (503) — onboarding cannot progress past the verification step | YES |
| 9 | Register the Middesk production webhook at `/api/webhooks/business-verification/middesk` | Test delivery from Middesk's own test mode returns 200 and is logged | Verification results never arrive — Businesses stay stuck pending | YES |
| 10 | Confirm Stripe production account; create the 4 standard Prices; set `STRIPE_SECRET_KEY`, `STRIPE_STARTER_PRICE_ID`/`STRIPE_CORE_PRICE_ID`/`STRIPE_GROWTH_PRICE_ID`/`STRIPE_SCALE_PRICE_ID`, `PLATFORM_BILLING_PROVIDER=stripe` | `npm run production-readiness` reports `STRIPE_BILLING: CONFIGURED` | Billing setup fails closed (503) — onboarding cannot progress past billing setup | YES |
| 11 | Map each Price ID to the correct plan code exactly — Starter/Core/Growth/Scale only, no Enterprise Price | `StripePlatformBillingProvider.requirePriceId` resolves correctly for every standard plan | A plan silently maps to the wrong price — financial correctness issue, not just availability | YES |
| 12 | Register the Stripe production webhook at `/api/webhooks/billing/stripe` (subscription + invoice events) | Stripe dashboard shows successful recent deliveries | Subscription/invoice state never syncs locally — Billing page will show stale/incorrect state | YES |
| 13 | Confirm the owner has reviewed `docs/PRODUCTION_LEGAL_REVIEW.md` | Owner sign-off recorded (outside this repo) | Launch proceeds on an un-reviewed legal/commercial basis — owner's explicit call, not this runbook's | NO (owner's explicit decision either way) |
| 14 | Confirm `CURRENT_LEGAL_DOCUMENT_VERSIONS` in `src/lib/legal/legalDocumentVersions.ts` matches whatever the owner actually approved | Versions match; no un-reviewed content silently differs from what was approved | A Business "accepts" different content than what was reviewed | YES |
| 15 | Confirm feature flags: no `FEATURE_*` override re-enables anything hidden for this launch | `src/lib/feature-flags.ts` defaults hold in production | An unfinished feature (Payments, Reports, etc.) becomes reachable | YES |
| 16 | Run `npm run production-readiness` against the real deployed environment's variables. **`CONFIGURATION_READY` means every required environment variable is present and structurally valid — it is NOT a claim that any provider has ever been successfully called.** Only step 18's smoke test and step 19's actual first-live-Business exercise establish `LIVE_VERIFIED` | `BUSINESS_PLATFORM: CONFIGURATION_READY`, `LIVE_VERIFIED: NO` (expected — this step never makes a live call), `FULL_MONEY_MOVEMENT: DISABLED` | Any `NOT READY`/`NOT CONFIGURED`/`CONFIGURATION_INCOMPLETE` for a P0 item from step 6-12 (includes all 4 Stripe standard-plan Price IDs and a genuinely non-localhost `APP_URL`) | YES |
| 17 | Deploy the application | Deployment succeeds; build matches this branch | Deployment fails/rolls back | YES |
| 18 | Run `node scripts/smoke-test.mjs --url <production-url>` | All checks pass (health, homepage, login, protected-route-denies-unauthenticated) | Any smoke check fails | YES |
| 19 | Begin `docs/FIRST_LIVE_BUSINESS_ACCEPTANCE.md` — controlled first Business | Each step in that document completes as described | Any step fails — stop and diagnose before inviting a second real Business | YES |
| 20 | Confirm tenant isolation during the controlled test: a second test organization cannot see the first's data | Isolation holds | Any cross-tenant leak | YES — IMMEDIATE STOP (see Section 65/this runbook's own incident doc) |
| 21 | Confirm Middesk/Stripe/Resend/Supabase outage behavior matches `docs/CODEX_P0_VERIFICATION_HANDOFF.md`'s documented expectations (no silent "success") | Each provider's failure mode is honest, never a fabricated success | A fabricated success under outage conditions | YES |
| 22 | Confirm rollback plan is understood (see `docs/OPERATIONS_BACKUP_RECOVERY.md`) before declaring the launch complete | Team knows the forward-fix-not-down-migration convention and has the Day-3 backup from step 3 | No one knows how to respond to a bad deploy | YES |
| 23 | Confirm monitoring/observability is actually receiving this deployment's structured logs | Logs for `business_verification_webhook_middesk`, `platform_billing_webhook_stripe`, etc. are visible wherever the team watches logs | No visibility into webhook/provider failures post-launch | NO (fix promptly, not necessarily before launch) |
| 24 | Confirm `FULL_MONEY_MOVEMENT` remains `DISABLED` in the production readiness report and that Payments stays hidden from navigation | Customer repayment money movement is not reachable by any user | Any path to customer money movement appears | YES — IMMEDIATE STOP |
